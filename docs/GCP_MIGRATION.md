# GCP migration (Northflank → Cloud Run)

Moves `dlbtrust-app` from the Northflank project `dlbtrust` (see
`docs/NORTHFLANK_MIGRATION.md`) into the existing Google Cloud project
`dlb-treasury-management`. Infrastructure is declared in `infra/gcp`
(Terraform); the data moves are scripted in `scripts/gcp`. Nothing here is
applied automatically — every step below is run by an operator, and the
`GCP Deploy` workflow stays disabled (`if: false`) until cutover.

## Target topology

| Northflank | GCP |
| --- | --- |
| combined service `dlbtrust-app` (Dockerfile, port 3002, 1 instance) | Cloud Run service `dlbtrust-app`, `min=max=1`, CPU always allocated — `infra/gcp/cloudrun.tf` |
| PostgreSQL 16 addon `dlbtrust-db` (private, TLS) | Cloud SQL for PostgreSQL 16, private IP only, PITR + 14 daily backups — `infra/gcp/cloudsql.tf` |
| volume `dlbtrust-data` at `/data` (RWO, 6 GiB) | GCS bucket `<project>-dlbtrust-app-data` mounted at `/data` via Cloud Storage FUSE |
| secret group `dlbtrust-runtime` (130 variables) | one Secret Manager secret per variable, injected as env vars — `infra/gcp/secrets.tf` |
| `runtimeEnvironment` in the service spec | `runtime_environment` variable (plain env vars) |
| addon URI aliased to `DATABASE_URL` | `DATABASE_URL` secret generated by terraform from the Cloud SQL user (unix-socket URL) |
| git build on Northflank, triggered by `northflank-deploy.yml` | Docker build in GitHub Actions → Artifact Registry → `gcloud run deploy` — `gcp-deploy.yml` |
| `NORTHFLANK_API_TOKEN` repo secret | Workload Identity Federation (keyless) — `infra/gcp/deploy_identity.tf` |
| `dlbtrust-fineract`, `openach` services | **not in this phase** — see "Out of scope" |

The service stays at exactly one instance for the same reasons it did on
Northflank: `/data/journal` and `/data/shutdown-state` assume a single writer,
and the in-process schedulers (OpenSanctions refresh, Spritz Buy / Melio status
sync) must not run twice. Cloud Run enforces this with `min=max=1`; CPU
throttling is disabled so those loops keep running between requests.

### Why Cloud Storage FUSE for `/data`

Cloud Run has no block volumes. The three things under `/data` — Melio CSV
exports, the executed Trustees Signature Page, journal/shutdown state — are
written whole-file by a single process, which is the access pattern FUSE
handles well. `MELIO_EXPORT_DIR` and `TRUST_SIGNATURE_DOCUMENT_PATH` keep
their values. Caveats to verify in the smoke test: FUSE does not support
`rename()` atomically and file locks are no-ops, so if
`server/integrations/backup/transactionJournal.js` relies on either, switch the
journal to the PostgreSQL state store (`pgStateStore.js`) before cutover.

## Order of operations

Prerequisites, all checked before anything is created:

- Billing enabled on `dlb-treasury-management` (`scripts/gcp/bootstrap.sh`
  refuses to continue otherwise). Cloud SQL is the only line item that bills
  while idle (~$10/mo for `db-g1-small`); Cloud Run at one always-on instance
  is ~$30–50/mo.
- `gcloud` authenticated as a project Owner (`gcloud auth login` +
  `gcloud auth application-default login`), Terraform ≥ 1.6,
  `cloud-sql-proxy`, PostgreSQL 16 client tools, `@northflank/cli`.
- `NORTHFLANK_API_TOKEN` with read access to the `dlbtrust-runtime` secret
  group and the `dlbtrust-db` addon.

```bash
# 0. state bucket + baseline APIs
GCP_PROJECT=dlb-treasury-management scripts/gcp/bootstrap.sh

# 1. secret names (no values) → terraform.tfvars
NORTHFLANK_API_TOKEN=... node scripts/gcp/migrate-northflank-secrets.mjs --list \
  > infra/gcp/terraform.tfvars

# 2. infrastructure. The first apply takes ~15 min (Cloud SQL + VPC peering).
cd infra/gcp
terraform init -backend-config="bucket=dlb-treasury-management-tfstate"
terraform plan -out plan.tfplan
terraform apply plan.tfplan
cd -

# 3. secret values (Northflank → Secret Manager, values never printed)
NORTHFLANK_API_TOKEN=... node scripts/gcp/migrate-northflank-secrets.mjs --dry-run
NORTHFLANK_API_TOKEN=... node scripts/gcp/migrate-northflank-secrets.mjs \
  --set APP_URL=https://<cloud run url> \
  --set SPRITZ_API_KEY=<the key created in Devin session cd2140f2, currently only in Devin's repo secrets>

# 4. first image (the workflow is disabled until cutover)
gcloud auth configure-docker us-east1-docker.pkg.dev
docker build -t us-east1-docker.pkg.dev/dlb-treasury-management/dlbtrust/dlbtrust-app:bootstrap .
docker push us-east1-docker.pkg.dev/dlb-treasury-management/dlbtrust/dlbtrust-app:bootstrap

# 5. ledger database. The script locks the `dlbtrust` role out and kills its
#    sessions for the duration, so a running Cloud Run instance cannot re-seed
#    tables mid-restore; it reconnects once the role is unlocked. Northflank
#    keeps writing (schedulers) — expect a few +1 row deltas on log tables
#    unless the Northflank service is paused (final cutover only).
#    Cloud SQL is private-IP only; the proxy needs a public IP on the instance
#    for the duration (IAM + TLS, no authorized networks).
curl -X PATCH -H "Authorization: Bearer $NORTHFLANK_API_TOKEN" -H 'Content-Type: application/json' \
  -d '{"externalAccessEnabled":true,"tlsEnabled":true}' https://api.northflank.com/v1/projects/dlbtrust/addons/dlbtrust-db
# EXTERNAL_POSTGRES_URI_ADMIN from GET .../addons/dlbtrust-db/credentials → SOURCE_DATABASE_URL
gcloud sql instances patch <instance> --assign-ip
gcloud sql users set-password postgres --instance <terraform output cloudsql_connection_name, last segment> --prompt-for-password
SOURCE_DATABASE_URL=... CLOUDSQL_CONNECTION_NAME=$(cd infra/gcp && terraform output -raw cloudsql_connection_name) \
CLOUDSQL_ADMIN_PASSWORD=... scripts/gcp/migrate-postgres.sh --dry-run
... scripts/gcp/migrate-postgres.sh
gcloud sql instances patch <instance> --no-assign-ip
curl -X PATCH ... -d '{"externalAccessEnabled":false,"tlsEnabled":true}' .../addons/dlbtrust-db

# 6. /data contents
NORTHFLANK_API_TOKEN=... DATA_BUCKET=$(cd infra/gcp && terraform output -raw data_bucket) \
  scripts/gcp/migrate-data-volume.sh

# 7. deploy the bootstrap image and smoke test
gcloud run deploy dlbtrust-app --region us-east1 \
  --image us-east1-docker.pkg.dev/dlb-treasury-management/dlbtrust/dlbtrust-app:bootstrap
```

`DATABASE_URL` is deliberately excluded from the secret migration, exactly as
it was excluded from the Fly → Northflank move: it is derived from the Cloud
SQL user so the app follows the instance if it is ever recreated.

## Smoke test before cutover

Run against the Cloud Run URL with the Northflank service still taking
production traffic. All calls are read-only or shadow-mode.

1. `GET /api/health/ready` → 200; `GET /api/health` reports the migrated
   bond/cash/trust/user counts (doubles as the database check).
2. `GET /api/vendors/payments/melio` lists the payment records (operator auth).
3. `MELIO_EXPORT_DIR=/data/melio-exports` is writable and
   `TRUST_SIGNATURE_DOCUMENT_PATH` resolves — check Cloud Run logs for the
   FUSE mount, then a canonical vendor-bill proposal in shadow mode writes a
   CSV that appears in the bucket.
4. `GET /api/finops/compliance/readiness` → ready (OpenSanctions ingest ran
   against Cloud SQL; the dataset is ~170k rows, so this is also a decent
   load test of the private-IP path).
5. `GET /api/finops/spritz/buy/readiness` → readiness ok with
   `live: false` (`SPRITZ_BUY_LIVE` unset) and the thirdweb destination
   `0x1A904F795a0511C31Ba6347504D08d1bA58E4f89` on Base.
6. Restart the revision (`gcloud run services update --no-traffic` then back)
   and confirm `/data/shutdown-state` and the journal were written and read
   back — this is the FUSE-semantics check from above.

Keep `MELIO_USE_API=false`, `SPRITZ_BUY_LIVE` unset and `PAYMENT_HUB_LIVE=false`
throughout: a live call creates real bills / debits.

## Cutover

1. Take a final `scripts/gcp/migrate-postgres.sh` and
   `migrate-data-volume.sh` run with the Northflank service scaled to zero
   (short write freeze; the maker/checker queue is in PostgreSQL, so nothing
   is lost, but approvals during the freeze fail).
2. Map the domain: `gcloud run domain-mappings create --service dlbtrust-app
   --domain <host>` and update DNS. Update `APP_URL`,
   `AS2_MESSAGE_ID_DOMAIN` and the CSP `connect-src` default, which currently
   point at `https://p01--dlbtrust-app--gcq8bn6c4zlp.code.run`.
3. Set the four `GCP_*` repository variables from `terraform output`, remove
   `if: false` from `.github/workflows/gcp-deploy.yml`, delete
   `.github/workflows/northflank-deploy.yml`.
4. Rotate: `SPRITZ_API_KEY` (already replaced), `NORTHFLANK_API_TOKEN` (no
   longer needed — revoke), and any credential that was ever read out of the
   Fly container by `migrate-fly-secrets.mjs`.
5. Keep the Northflank project for 14 days as rollback (DNS back + resume
   secrets), then delete it.

## Financial-data gaps this closes (and does not)

Moving the host does not by itself change how payouts or payments move. What
the GCP platform adds, once the service is there:

- **Durable, queryable transaction history**: Cloud SQL PITR + the
  `canonical_payments` / GL tables become exportable to BigQuery with a
  federated query or Datastream, which is the base for reconciliation reports
  across Spritz, Melio, ACH and stablecoin rails (Option A from the planning
  message; a follow-up).
- **Secret hygiene**: every rail credential (Spritz, Melio, Moov, thirdweb,
  Fineract) is versioned in Secret Manager with audit logging, instead of a
  single Northflank secret group.
- **Gemini**: `GEMINI_API_KEY` (created in this session, bound to the
  `firebase-adminsdk` service account, restricted to the Gemini API) can be
  added to `secret_names` when a use — e.g. transaction categorisation or
  reconciliation exception summaries — is wired in. It is not used by the
  app yet.

What still requires product work, not infrastructure: a linked Spritz funding
source (Plaid, dashboard-only), `MELIO_API_CONTRACT_VERIFIED`, and any live
flag flip. None of those are touched by this migration.

## Out of scope for this phase

- `dlbtrust-fineract` (Apache Fineract GL) and `openach` (PHP ACH
  origination) keep running on Northflank; `FINERACT_URL` / OpenACH URLs must
  stay reachable from Cloud Run (public HTTPS or a VPN). Moving them means
  Cloud Run + a second Cloud SQL each, or GKE Autopilot for Fineract's memory
  footprint — decide after the main service is stable.
- Cloud Armor / IAP in front of the operator console — recommended, separate
  PR.
- Fineract-side GL export to BigQuery.
